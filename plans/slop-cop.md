# Slop Cop implementation plan

## Status

Implemented in `dev-tools/slop-cop/` with the analysis and reporting workflows in
`.github/workflows/`. Local validation is complete. Live artifact, permission,
comment, override, and required-check behavior still requires post-merge GitHub
workflow validation.

## Executive decision

Build **Slop Cop** as a small, repository-owned Python project that reviews
changed English-language Dev Notes for high-confidence LLM artifacts, clichéd
rhetorical constructions, overused vocabulary, and repeated writing patterns.
Its projector, built-in rules, scoring, and reporting remain deterministic and
offline. Trusted repository-owned custom rules may implement arbitrary logic,
including asynchronous calls to a configured judging service.

Slop Cop is an editorial linter, not an AI-authorship detector. Its score means
“how many configured editorial-risk signals are present,” not “the probability
that an LLM wrote this text.” Human prose can trigger the rules and LLM prose can
avoid them. The CLI, report, check name, and documentation must preserve that
distinction.

The initial product has four outputs:

- precise, source-mapped findings with an explanation and suggested editorial
  action
- a transparent score from 0 to 100 for each changed Dev Note
- a required CI decision based on an absolute score threshold and any
  unsuppressed blocking findings
- a self-contained HTML report uploaded as a short-lived PR artifact, with a
  concise sticky PR comment linking to it

Keep the implementation under `dev-tools/slop-cop/` and the GitHub integration
under `.github/workflows/`. Do not persist generated reports in the repository.

## Locked implementation choices

Treat these as decided unless implementation evidence makes one impossible:

| Concern | Choice |
| --- | --- |
| Runtime | Python 3.12 or newer |
| Packaging and execution | One self-contained `uv` project and committed `uv.lock` |
| Typed validation | Pydantic v2 frozen models; `tomllib` loads TOML before validation |
| Unicode matching | The `regex` package with reviewed patterns and per-operation timeouts |
| External HTTP | One shared `httpx.AsyncClient`; tests use `httpx.MockTransport` |
| Concurrency | One `asyncio` pipeline with bounded tasks, a shared semaphore, and stable result sorting |
| Markdown handling | Repository-scoped same-length source projector; no rendered-HTML round trip |
| HTML generation | Python standard-library escaping and direct template functions; no browser framework or required JavaScript |
| Test and quality tools | `pytest`, `pytest-asyncio`, Ruff, and mypy |
| Default threshold | 80, subject only to the defined calibration gate |
| PR aggregation | Minimum score across changed Dev Notes; every changed file must pass |
| Built-in network behavior | None |
| Custom network behavior | Trusted Python rules through named JSON services |
| Initial custom registry | `CUSTOM_RULES = ()`; service-backed behavior is proven with temporary test rules, not a shipped placeholder rule |
| Default services | None configured or enabled |
| CI trust boundary | Base-revision analyzer for enforcement; candidate analyzer only for unprivileged preview/tests |
| PR reporting | Unprivileged artifact workflow plus trusted `workflow_run` sticky-comment workflow |

The exact phrase inventory, per-rule weights, density windows, and category
density policies are calibrated deliverables. The contracts, formulas, safety
bounds, and acceptance tests that constrain those values are not optional.

There are no implementation-blocking product choices left open in this plan.
When calibration changes a candidate value, record the before/after fixture
results and keep the locked contracts intact rather than requesting a new design
decision.

## Goals

1. Catch high-confidence AI detritus and recurring “LLM voice” patterns before
   a Dev Note is merged.
2. Keep built-in analysis deterministic and offline, and keep every score
   explainable from validated rule outputs even when a custom external judge is
   nondeterministic.
3. Minimize false positives on legitimate technical prose, Markdown structure,
   product names, code, links, generated bylines, and image markup.
4. Make rules easy to add, remove, update, disable, inspect, and test through
   declarative configuration or one small repository-owned Python interface.
5. Make one ordinary phrase a useful observation rather than a failed build;
   repeated and diverse signals should carry progressively more weight.
6. Prevent a long clean passage from hiding a bad section or one clean file from
   hiding a bad file.
7. Make overrides deliberate, reasoned, attributable, bound to the current PR
   revision, and visible in the report.
8. Produce a useful report on both pass and fail, including exact source
   locations, category totals, scoring math, and base-versus-head changes.
9. Keep local and CI behavior identical by making the workflow call the same
   versioned CLI and configuration developers can run locally.
10. Establish a compact evaluation corpus and regression suite so rule changes
    improve measured behavior rather than merely adding more regexes.

## Non-goals

- Determining whether a person or model authored a document.
- Shipping a built-in LLM judge, model-provider integration, prompt-management
  layer, or generic service-orchestration framework. A repository-owned custom
  rule may call a specifically configured service.
- Rewriting prose or applying automatic fixes.
- Building an MCP server, editor extension, web application, hosted dashboard,
  general linting platform, external plugin API, or package publishing pipeline.
- Supporting arbitrary document formats, repositories, languages, or house
  styles in the first version.
- Scanning source code, project documentation, issues, PR descriptions, commit
  messages, or comments. The first enforcement target is
  `docs/dev-notes/posts/*.md`.
- Treating every bold lead-in, list, triad, horizontal rule, or polished sentence
  as suspicious. These are normal structures in the current Dev Note style.
- Maintaining a historical database of scores or generated HTML reports.
- Rendering the HTML artifact as a public website. GitHub PR comments cannot
  embed an HTML document, and GitHub artifact links download artifacts rather
  than hosting them. The comment will show the summary and link to the artifact.

## Product and policy principles

### Write only for the implementation

Documentation, docstrings, comments, rule descriptions, configuration examples,
test names, CLI text, and reports must describe only Slop Cop's current behavior
and repository requirements. Do not include design history, product comparisons,
or origin stories. Write rule definitions, descriptions, and tests directly from
the behavior required in this repository.

Comments should explain a local invariant, non-obvious algorithm, safety bound,
or repository-specific policy. Omit comments that only narrate what the next
line does or recount how the design was reached. Rule metadata should state what
the rule detects, when it applies, why it matters to a Dev Note, and what an
editor can do about it.

### Detect editorial signals, not authorship

Use neutral language such as “finding,” “signal,” “repetition,” and “editorial
risk.” Do not label an author, paragraph, or document as AI-generated. A failed
check means that the configured editorial policy was not met.

### Prefer precision over a large rule count

A small high-quality rule set is more useful than hundreds of noisy matches.
Every scored rule must have positive examples, legitimate counterexamples, a
stable identifier, a concise rationale, and an explicit scoring policy. New
rules remain advisory until their precision is demonstrated by fixtures and
real Dev Notes.

### Keep findings and scoring separate

Rules identify occurrences. A scoring layer deduplicates related findings,
applies allowances, caps penalties, and calculates the decision. This allows
the report to show all useful evidence without charging several regexes for the
same phrase.

### Treat concentration as independent evidence

For selected rules, the same number of findings should cost more when packed
into one passage than when spread across a long note. Support both document-wide
allowances and opt-in rolling passage-density penalties. Appending clean prose
must not dilute a dense problematic passage. Density remains rule-specific and
bounded; do not apply one universal document-density formula to every finding.

### Analyze rendered prose while preserving source positions

Markdown syntax and generated content are inputs, but most are not prose. Build
a source-preserving projection that masks ignored characters with spaces and
retains all newlines. Rules run on that projection while every finding maps
exactly to the original path, code-point span, line, and column.

### The absolute threshold owns enforcement

Analyze both the base and head version where available, but gate on the head
version. A favorable delta is context, not an exemption. This avoids permanently
grandfathering weak prose. A manual override handles an intentional exception.

### The worst changed note owns the PR score

Score every changed Dev Note independently. Define the displayed PR score as the
minimum file score and require every changed file to pass. Do not use a
word-weighted average that lets one long clean note conceal another failing note.

## Intended user experience

### Local commands

The primary interface is intentionally small:

```text
uv run --project dev-tools/slop-cop slop-cop check \
  --config dev-tools/slop-cop/slop-cop.toml \
  docs/dev-notes/posts/example.md

uv run --project dev-tools/slop-cop slop-cop check \
  --config dev-tools/slop-cop/slop-cop.toml \
  --baseline-ref origin/main \
  --html-dir /tmp/slop-cop-report \
  --json /tmp/slop-cop-report/report.json \
  docs/dev-notes/posts/example.md

uv run --project dev-tools/slop-cop slop-cop explain rhetoric.not-just
uv run --project dev-tools/slop-cop slop-cop list-rules
```

`check` prints a compact terminal summary and annotated findings. It exits:

| Code | Meaning |
| --- | --- |
| `0` | Every analyzed file passes, or a valid CI override was supplied |
| `1` | Analysis completed and at least one file failed policy |
| `2` | Input, configuration, Markdown projection, or report generation failed |

`check` must finish writing requested JSON and HTML outputs before returning
exit code `1`. The workflow runs that step with `continue-on-error`, uploads the
completed outputs, then uses a separate final step to reproduce the saved
decision as the job conclusion. Do not add an exit-zero or no-enforcement CLI
option.

### Terminal output

Terminal output should include:

- file and PR score, threshold, pass/fail/overridden state
- base score and delta when a base version exists
- category penalties, document allowances, passage-density bonuses, and the
  exact final-score arithmetic
- `path:line:column`, rule ID, matched excerpt, points charged, and advice for
  every unsuppressed finding
- suppressed and advisory counts without expanding them by default
- the command needed to generate the HTML report locally

Support a stable JSON schema for CI and tests. Avoid SARIF in the first version;
GitHub annotations plus the HTML report cover the immediate use case, and SARIF
would add another contract without improving the initial decision quality.

## Normative execution order

Use one orchestration path for local use and CI:

1. Load TOML with `tomllib` and validate the complete config with Pydantic.
2. Build and validate the immutable rule registry and effective policies.
3. Read each bounded source file and build its same-length prose projection.
4. Segment the projection once into shared tokens, sentences, and paragraphs.
5. Construct immutable `RuleContext` and `RuleRuntime` values.
6. Evaluate enabled rules with bounded async concurrency and shared deadlines.
7. Validate every `RuleEvaluation` and convert its signals to source-mapped
   findings; translate rule failures according to `on_error`.
8. Apply source suppressions, overlap groups, and primary/related finding
   selection.
9. Calculate document allowances, passage-density costs, rule costs, category
   density/caps, file scores, and the run decision in that order.
10. Analyze the base document through the same steps when comparison is enabled.
11. Serialize one `RunResult`; terminal, JSON, HTML, annotations, job summary,
    and PR comment are projections of that result and never rerun rules or
    recalculate scoring.

No rule, renderer, or workflow step may reorder or bypass these boundaries.

## Core data contracts

Use immutable typed records for the analysis boundary.

### `Document`

Contains the source path, original text, prose projection, line-start index,
front-matter metadata needed for context, analyzable word/sentence/paragraph
counts, and masked ranges with reasons.

### `Rule`

Define a small, stable asynchronous `Rule` protocol in `rules/api.py`. Separate
what a rule detects from how repository policy scores it.

`RuleMetadata` belongs to Python/declarative rule definitions and contains:

- stable ID such as `rhetoric.not-just`
- positive integer rule version, incremented when matching or external response
  interpretation changes
- category and short title
- rationale and editor-facing advice
- contexts in which the rule is eligible
- execution kind: `local` or `external`
- required named services for an external rule

`RulePolicy` belongs to `slop-cop.toml` and contains:

- enabled state and severity
- blocking state
- maximum units allowed from one signal
- fixed and optional document-density allowance
- first/repeat costs and rule cap
- optional rolling-passage density policy
- failure policy: `fail` or `advisory`, defaulting to `fail` for a scored
  external rule in the required profile
- validated rule-specific settings

Every enabled Python rule must have exactly one policy block. A declarative rule
defines its metadata, matcher, and policy in one TOML block. Registry construction
produces immutable `ConfiguredRule` values; the engine and scorer consume those
rather than consulting configuration during evaluation.

Limit implicit policy defaults to `enabled = true`, `blocking = false`, and
`on_error = "fail"`. Every scored rule must state severity, allowances, first and
repeat costs, and caps explicitly. Advisory zero-point rules must state that
policy explicitly as well.

Use only `info`, `warning`, and `error` severities. `info` rules are advisory and
must have zero costs; `warning` rules may affect the score; `error` rules must be
blocking. Severity describes policy impact, not authorship confidence.

Each Python rule has one evaluator that accepts `RuleContext` and `RuleRuntime`
and returns a validated `RuleEvaluation` without calculating the document score.

`RuleContext` supplies the source-preserving prose view, tokens, sentences,
paragraphs, repository vocabulary, bounded helper methods, and an explicit
method for selecting the content sent to an external service. `RuleRuntime`
supplies a shared deadline, credential-backed named-service HTTP access,
response-size limits, and content-safe diagnostics; it does not expose raw
secret values through the rule API.

`RuleEvaluation` contains an ordered tuple of `RuleSignal` values and bounded
audit metadata. A signal contains:

- a stable normalized key
- chargeable units in a configured, validated range
- either an exact source span or explicit `document` scope
- optional exact evidence spans
- bounded editor-facing detail

Literal and regex rules normally return one unit per exact span. A document-level
judge may return one signal with a bounded strength, plus evidence spans when the
service supplies quotations that can be mapped back to the source exactly. The
engine maps signals into findings and configured score costs. Custom rules may
not set the final score, threshold, pass/fail state, or override state directly.
This preserves transparent centralized scoring while allowing custom logic to
drive a rule's evidence and strength.

Only signals with an exact primary source span participate in local
passage-density calculations. A document-scoped custom signal participates only
in document-wide allowance and cost; its evidence spans are display evidence and
do not duplicate its units into density windows. A custom rule that needs local
density must emit separate exact-span signals.

The engine adds shared metadata and creates findings so custom rules do not
repeat line mapping, suppression, overlap, scoring, serialization, or report
boilerplate. Built-in synchronous algorithms use an adapter that returns an
already-completed async evaluation; do not maintain separate sync and async rule
pipelines.

`rules/registry.py` constructs one validated registry from three explicit
sources in a fixed order:

1. built-in Python rules from `rules/builtins/`
2. declarative phrase and regex rules from `slop-cop.toml`
3. repository-owned Python rules exported as `CUSTOM_RULES` from
   `rules/custom/__init__.py`

Do not discover installed packages, Python entry points, or environment modules.
The single `CUSTOM_RULES` export is the algorithmic extension point. Custom rule
code is trusted code with the same process authority as Slop Cop and may use
committed project dependencies and declared named services through
`RuleRuntime`; it is not sandboxed. This keeps custom code easy to find and
review without making Slop Cop a plugin host.

### `Finding`

Each occurrence contains:

- rule ID, category, and severity
- source path, start/end offsets, line, column, and bounded excerpt
- normalized match key used for repetition and overlap handling
- score group used to prevent double charging
- explanation and suggested editorial action
- whether it is advisory, chargeable, suppressed, or blocking
- suppression reason where applicable

Never put full document content in logs, annotations, or error messages. The
local HTML report may show bounded surrounding context and an escaped highlighted
view of the changed note.

### `FileResult` and `RunResult`

`FileResult` contains document metrics, findings, suppressions, per-rule costs,
document and peak-density measurements, density-window locations, category
costs, score, threshold, hard-fail state, and optional base comparison.
`RunResult` contains all file results, the minimum PR score, final decision,
override metadata, rule execution errors, external-rule audit records, tool
version, configuration digest, and base/head revisions.

Use separate enums so reporting never conflates completion with policy:

- `analysis_state`: `complete`, `incomplete`, `error`, or `not_applicable`
- `decision`: `pass`, `fail`, `overridden`, or `not_applicable`

An advisory external-rule error can therefore be `analysis_state = incomplete`
with `decision = pass`; a required error is `analysis_state = error` with
`decision = fail`; and a valid manual override changes only `decision` to
`overridden`.

Version the JSON representation from the first release. The trusted reporting
workflow must reject unknown versions instead of guessing.

## Custom-rule runtime and external judges

Custom Python rules may perform local algorithms or call a named HTTP service.
Keep this capability narrow: Slop Cop owns a bounded JSON transport, while the
custom rule owns request construction, response schema validation, and mapping
the service result into `RuleSignal` values.

A custom rule may use arbitrary local Python logic and committed dependencies.
Any service-backed rule enabled in the required CI profile must route network
access through the named-service runtime so deadlines, destination policy,
credentials, response bounds, audit fields, and content-safe failures remain
enforceable. Direct sockets, subprocess-based clients, and ad hoc SDK transports
are not allowed for required CI rules.

### Named services

Define external endpoints in trusted base-revision configuration:

```toml
[services.editorial_judge]
url = "https://judge.internal.example/v1/evaluate"
token_env = "SLOP_COP_EDITORIAL_JUDGE_TOKEN"
timeout_seconds = 20
max_response_bytes = 65536
max_attempts = 1
required_judge_revision = "editorial-v1"
```

Validate service names, HTTPS URLs, host allowlists, timeout bounds, response
limits, required judge revisions, and environment-variable names at startup.
Permit plaintext HTTP only for an explicitly configured loopback test service.
The configuration names a secret environment variable but never contains the
secret value. Treat the configured URL's scheme/host/port as the exact allowed
origin, reject redirects, and do not let a rule append or replace the origin.

An external rule declares the service names it uses. `RuleRuntime` exposes only
those named clients and never returns the raw bearer token to the rule. The
shared client applies authentication, deadline propagation, connection and
response limits, content-safe error translation, and an idempotency key derived
from the rule ID, rule version, configuration digest, and analyzed-content hash.
Retries are disabled by default; enable a bounded retry only for a service whose
contract makes the request idempotent.

### External evaluation contract

External rule code must:

1. choose the exact projected prose or passages to send; ignored Markdown
   contexts never leave the runner
2. send Dev Note content as data in a structured JSON field
3. require a versioned structured JSON response
4. validate every enum, strength, detail length, count, and evidence item
5. map quoted evidence back to a unique exact source span or omit the span and
   emit a document-scoped signal
6. require the configured judge revision and reject a mismatched or absent
   revision
7. reject unknown response fields when the service schema is strict
8. return no raw prompt, response, token, or unbounded service text in a finding

If the service uses an LLM, its service-side judge must run without tools and
return only the response schema expected by the custom rule. Treat document text
as untrusted input that cannot select endpoints, credentials, models, prompts,
score weights, or CI outcomes.

### Timeouts, concurrency, and failures

Apply a run-wide external-evaluation concurrency limit, a per-rule timeout, and
the overall CLI deadline. Cancel outstanding external evaluations when the run
deadline expires. Preserve stable finding order by sorting completed evaluations
by configured rule order and source position, never network completion order.

Use these failure semantics:

| Condition | Result |
| --- | --- |
| Required setting or secret missing | Rule execution error |
| Timeout, transport error, invalid JSON, oversized response, or schema violation | Rule execution error |
| Missing or mismatched required judge revision | Rule execution error |
| `on_error = "fail"` | File and CI fail as an analysis error; do not manufacture a score penalty |
| `on_error = "advisory"` | Score is calculated without that rule and the report is visibly `INCOMPLETE` |

An external rule that contributes to the required CI threshold must use
`on_error = "fail"`. Advisory failure is for experimental reporting rules only.
A manual override may override the final CI failure but must not rewrite the rule
error as a successful evaluation.

### Audit and privacy

For each external evaluation, record the rule ID/version, named service,
endpoint hostname, analyzed-content hash, request/response schema versions,
service request ID when provided, reported judge/model revision when provided,
attempt count, latency, outcome, and a response digest. Never record credentials,
authorization headers, complete request bodies, raw prompts, or raw responses.

Mark every external rule as “sends prose to `<hostname>`” in `list-rules`,
`explain`, terminal output, JSON, and HTML. Built-in and declarative rules never
send content. Enabling an external rule is therefore an explicit repository
policy change visible in configuration and code review.

## Markdown-aware prose projection

The projector is the main false-positive control and should be implemented
before expanding the rule catalog.

Starting with the original source, replace ignored characters with spaces while
preserving `\n` exactly. Mask:

- YAML front matter, including the duplicated title and description
- the generated range between `<!-- dev-note:byline:start -->` and
  `<!-- dev-note:byline:end -->`
- fenced code blocks using backticks or tildes
- inline code spans, with correct handling of variable-length backtick fences
- HTML comments and tag markup/attributes while retaining visible text nodes
  such as `<figcaption>` content
- Markdown link and image destinations while retaining ordinary link labels
- Markdown image alt text by default, because it follows accessibility rather
  than article-prose conventions
- quoted block content by default so attributed prose is not scored against the
  author; make this setting explicit in the Dev Notes profile
- Slop Cop suppression directives themselves

Read source as strict UTF-8 after enforcing the raw-byte size limit. Reject
invalid UTF-8 and NUL characters. Do not normalize line endings or rewrite the
source before projection.

Use this source-map contract:

- offsets are zero-based Python string/code-point offsets
- displayed lines and columns are one-based
- `len(document.prose_projection) == len(document.source)`
- every `\n` and `\r` remains at its original offset
- every masked non-newline character becomes one ASCII space
- masked intervals are sorted, non-overlapping, and tagged with one or more
  reasons
- a projected span maps to the identical `[start, end)` source span without a
  lookup table or reconstructed text search

Implement ordered masking passes for front matter/generated ranges,
fenced/inline code, comments and HTML tags, link/image destinations, blockquotes,
and suppression directives. Each pass adds intervals; one final interval-union
step produces the projection. Do not repeatedly rewrite the text or let pass
order change source offsets. Unit-test every pass alone and in overlapping
combinations.

Scan headings, paragraphs, list-item prose, table-cell prose, emphasis text,
link labels, and visible raw-HTML text nodes. Treat captions as prose. Do not
strip punctuation before sentence and rhetorical-template analysis.

Segment only the projection. Use Unicode NFKC plus `casefold()` for comparison
keys while retaining original spans and excerpts. Define a word as a Unicode
letter/number token with internal combining marks and apostrophes; keep product
hyphens only when surrounded by token characters. Split paragraphs at blank
projected lines and Markdown block boundaries. Split sentences with a documented
punctuation heuristic plus a small tested abbreviation set; do not add a model or
large NLP dependency. Store every token/sentence/paragraph as an exact source
span so word-, sentence-, and paragraph-density windows share the same mapping.

The projector must detect malformed or unterminated front matter, generated
markers, code fences, and suppression ranges. Fail with a source location rather
than analyzing an ambiguous partial projection.

Use the current rendered Dev Note as an integration fixture. Assert that changes
inside its front matter, generated byline, code, link destinations, image tags,
or ignored quotes do not affect the score, while equivalent visible-prose
changes do.

## Initial rule portfolio

The first release should cover the following families. The checked-in registry
and configuration will contain the exact phrases, regexes, allowances, and
tests; this plan deliberately does not freeze an uncalibrated list of hundreds
of tokens.

Implement this minimum rule inventory. IDs are normative; split a listed family
only when its matching or scoring behavior genuinely differs:

| Rule IDs | Initial enforcement |
| --- | --- |
| `artifact.ai-disclosure`, `artifact.chat-preamble`, `artifact.continuation-offer`, `artifact.placeholder`, `artifact.instruction-residue` | Blocking only for unambiguous cases; otherwise scored |
| `rhetoric.not-but`, `rhetoric.not-just`, `rhetoric.no-no`, `rhetoric.imperative-reframe` | Scored with nonzero allowance and opt-in density |
| `rhetoric.dramatic-fragment`, `rhetoric.throat-clearing`, `rhetoric.testament`, `rhetoric.crucial-role`, `rhetoric.landscape-metaphor`, `rhetoric.formulaic-certainty`, `rhetoric.parallel-negation` | Scored only after counterexample calibration; otherwise advisory |
| `vocabulary.stock.<phrase-slug>` | One declarative rule per exact phrase; low weight, nonzero allowance, density-sensitive |
| `repetition.ngram`, `repetition.sentence-opener`, `repetition.template-shape`, `repetition.emphatic-fragments`, `repetition.hedge-stack`, `repetition.question-answer` | Scored after minimum-count and distinct-paragraph boundaries pass calibration |
| `attribution.vague-authority`, `attribution.citationless-study` | Low-weight scored or advisory when citation proximity is ambiguous |
| `ending.participial-tail`, `ending.generic-explanation` | Advisory until calibrated on complete Dev Notes |
| `structure.bold-leadins`, `structure.triad`, `structure.bullet-run`, `structure.horizontal-rules`, `structure.duplicate-title` | Advisory with zero points in the initial release |

Every exact stock phrase receives its own stable declarative ID, cases, and
policy. Do not hide a large phrase list behind one finding ID; editors must be
able to disable, tune, suppress, or remove one phrase without affecting others.

### 1. Pasted assistant artifacts

High-confidence examples include chatbot preambles, “as an AI” disclosures,
offers to continue or provide more detail, answer-format residue, unfinished
placeholders, and instructions addressed to the requester rather than the Dev
Note reader.

These rules may be `blocking = true` when the phrase is unambiguous in prose.
Ambiguous phrases remain scored rather than blocking. Code examples and quotes
are excluded by the projector.

### 2. Canned rhetorical templates

Implement these construction families:

- `not X, but Y`, `not just X`, and repeated `no X, no Y` contrasts
- imperative reframings such as `don't X it; Y it`
- dramatic fragments such as `the punchline?` and canned invitations to pause
- “worth noting/naming,” “it is important to note,” and similar throat clearing
- “a testament to,” “plays a crucial role,” and stock landscape metaphors
- formulaic certainty such as “you already know” and “X is everything”
- chained “did not” or equivalent parallel negations

Use syntax-aware boundaries and captured terms rather than naive substring
matches. A single common contrast should normally fit within its allowance;
multiple instances or several different template families should cost more.

### 3. Curated AI-associated vocabulary and stock phrases

Maintain a reviewable phrase table with stable sub-identifiers and exceptions.
Match words by token/lemma-like boundaries and phrases with whitespace and
punctuation normalization. Avoid substring matches inside product names,
identifiers, URLs, and code.

Vocabulary is weak evidence by itself. It should have a nonzero allowance,
small point values, and a category cap. Repeated use and clusters across several
paragraphs are more meaningful than one occurrence.

### 4. Repetition and rhythm

Add deterministic checks that generalize beyond a phrase catalog:

- repeated normalized 2–5 word phrases across distinct prose paragraphs
- repeated sentence openings after removing articles and transition words
- repeated rhetorical-template shapes even when their captured nouns differ
- clusters of short emphatic fragments
- stacked hedges or intensifiers in a bounded passage
- repeated question-then-answer setup patterns

Exclude stopword-only n-grams, headings repeated in navigation-like contexts,
configured product terms, and phrases whose repetition is expected in technical
explanation. Require distinct paragraphs for the strongest repetition penalties.

### 5. Vague attribution and trailing explanation patterns

Detect vague appeals such as unnamed experts or studies only when an attribution
construction lacks a nearby citation/link. Detect excessive participial tails
and generic explanatory endings as low-weight signals. These rules need strong
counterexamples because they are easy to overgeneralize.

### 6. Structural observations

Report, but initially assign zero points to, patterns such as repeated bold
lead-ins, triads, long bullet runs, frequent horizontal rules, and repeated
titles. The current Dev Note legitimately uses several of these structures.
Promote a structural rule to scored status only after the evaluation corpus
establishes a useful precision boundary.

## Overlap and deduplication

Several rules can describe the same text. Before scoring:

1. Group findings that overlap materially or share a configured score-group key.
2. Select the most specific/high-confidence finding as the chargeable primary.
3. Retain the others as related observations in the report with zero additional
   points.
4. Count a repeated template once per sentence unless the rule explicitly
   defines multiple independent captures.
5. Apply per-rule allowances only after overlap deduplication.

Test common collisions, especially `not just` within `not X but Y`, stock phrases
that also contain vocabulary tokens, and repeated phrases found by both a
specific cliché rule and the generic n-gram rule.

## Scoring model

### Meaning of the score

`100` means no chargeable findings under the configured profile. Lower values
mean more or stronger configured signals. The score is not a probability,
percentile, grade of factual correctness, or general measure of writing quality.

Use a default Dev Notes threshold of **80**. Treat this as an initial calibrated
policy value, not a universal standard.

### Rule cost

Every rule declares:

- `allowance`: a fixed number plus, where appropriate, a document-density policy
  with a natural opportunity unit, opportunity interval, and allowed units per
  interval
- `first_cost`: points for the first chargeable unit
- `repeat_cost`: points for each additional chargeable unit
- `rule_cap`: the maximum points one rule can remove
- optional `blocking`: whether any unsuppressed chargeable match independently
  fails policy

For rule `r` in document `D`:

```text
document_excess_r = max(0, deduplicated_units_r - allowance_r(D))

base_cost_r = 0                                           if document_excess_r == 0
base_cost_r = first_cost_r +
              repeat_cost_r * (document_excess_r - 1)    otherwise
```

`deduplicated_units_r` is the sum of bounded units from primary signals after
overlap handling. Literal matches normally contribute one unit. A custom judge
may contribute more than one only within the rule's configured maximum signal
strength; it still cannot bypass the rule or category cap.

`allowance_r(D)` must use the natural opportunity for that rule. For example, a
phrase rule may use words, a sentence-opening rule sentences, and a paragraph
pattern paragraphs. An optional document-density allowance is explicit:

```text
allowance_r(D) = fixed_allowance_r +
    floor(opportunities_r(D) / opportunity_interval_r) *
    allowed_units_per_interval_r
```

Do not use one global “violations per 1,000 words” divisor for all rules, because
each rule has a different natural opportunity and concentration behavior.

For very short documents, use a rule's fixed allowance rather than inflating a
density. If no analyzable prose remains, return an analysis error instead of an
automatic score of 100.

### Passage-density cost

Rules whose significance depends on concentration declare a `density` policy:

- `unit`: `word`, `sentence`, or `paragraph`
- `window`: the number of natural units in one rolling passage
- `allowed_units`: signal units permitted inside one window
- `first_cost` and `repeat_cost`: the passage-density penalty curve
- `cap`: the maximum additional points concentration can remove

Generate source-ordered rolling windows aligned to the selected natural unit and
advance by one unit. Calculate each window from primary, unsuppressed,
source-mapped signals after overlap deduplication:

```text
window_excess_r(w) = max(0, signal_units_r(w) - allowed_units_r(w))
peak_excess_r = max(window_excess_r(w) for w in windows(D))

density_cost_r = 0
    if peak_excess_r == 0
else min(density_cap_r,
         density_first_cost_r +
         density_repeat_cost_r * (peak_excess_r - 1))

rule_cost_r = min(rule_cap_r, base_cost_r + density_cost_r)
```

The densest window supplies the rule's local-density bonus. Using the peak rather
than summing overlapping rolling windows prevents the same signal from being
charged repeatedly. Additional clusters still affect the document-wide base
cost. The density bonus intentionally adds a bounded penalty for concentration;
it is not an overlapping-detector duplicate.

For the configuration example below, a note of at least 1,000 words can allow
two `rhetoric.not-just` units document-wide. If those units fall in separate
three-paragraph windows, the rule costs zero. If both fall within one
three-paragraph window, `peak_excess = 1` and the rule incurs the configured
two-point density cost even though its document-wide allowance is not exceeded.

For categories where several different weak rules clustered together are
meaningful, allow an equivalent optional category-density policy. Aggregate the
primary source-mapped signals for that category, calculate one peak passage
bonus, and include it before the existing category cap:

```text
category_cost_c = min(
    category_cap_c,
    sum(rule_cost_r for r in category c) + category_density_cost_c,
)
```

`category_density_cost_c` is zero when the category has no density policy.

Do not apply local density to blocking artifacts, a rule with only
document-scoped signals, or a rule/category without an explicit density policy.
Calibrate density windows and costs separately for vocabulary, rhetorical
templates, repeated openings, and other families whose isolated occurrences are
weak but clustered occurrences are strong.

### Category and final cost

Assign every scored rule to exactly one penalty category. Apply a cap after
summing rule costs and any configured category-density cost:

```text
category_cost_c = min(
    category_cap_c,
    sum(rule_cost_r for r in category c) + category_density_cost_c,
)
score = max(0, round(100 - sum(category_cost_c)))
```

Initial caps should reserve meaningful room for different evidence families:

| Category | Initial cap | Policy intent |
| --- | ---: | --- |
| Pasted artifacts | 100 | One unambiguous artifact may block independently |
| Rhetorical clichés | 25 | Repetition matters; one construction should not fail |
| Vocabulary/stock phrases | 15 | Weak evidence cannot dominate the score |
| Repetition/rhythm | 25 | Generalized patterns should matter without a phrase match |
| Attribution/explanation | 15 | Useful but more context-sensitive evidence |
| Structure | 0 | Advisory during the initial release |

These values are starting hypotheses. Lock final defaults only after the
calibration phase, and record any change in golden score tests and the project
changelog.

### File and PR decisions

A file passes only when:

```text
file_score >= configured_threshold
AND no unsuppressed blocking finding exists
AND no fatal analysis or `on_error = "fail"` rule error exists
```

An `on_error = "advisory"` rule error does not fail this expression, but the file
and run remain visibly `INCOMPLETE`; it must never be rendered as a fully clean
evaluation.

The PR score is `min(file_score)` over changed, non-deleted Dev Notes. Every file
must pass. A PR with no changed Dev Notes is neutral and the analysis job should
exit successfully without creating a misleading 100 score.

Analyze the base revision when a matching pre-change file exists. Show added,
removed, and persistent findings plus the score delta, but do not weaken the
absolute head threshold because the base was worse.

Classify finding changes as a deterministic multiset diff keyed by rule ID,
normalized match key, and score group. Pair equal keys in source order; unmatched
head instances are added and unmatched base instances are removed. Do not use an
LLM or fuzzy semantic comparison to decide persistence.

Run the same enabled rule set and policy against base and head, including
external rules, and retain separate audit records. Reuse an evaluation within
the run when rule ID/version, configuration digest, and projected-content hash
are identical. A base-only evaluation failure makes the comparison
`INCOMPLETE` and leaves the base score/delta null; it does not fail an otherwise
valid head evaluation. Only head errors participate in the CI decision.


The `custom.editorial-judge`, `custom.empty-intensifier`, and
`custom.generic-promise` blocks demonstrate the schema and are not part of the
initial checked-in configuration. The initial configuration contains only
production built-in/declarative rules, no named services, and an empty
`CUSTOM_RULES` tuple. Tests construct temporary local and external custom rules
to prove the extension contracts.

Use the version-1 field names shown above. Add fields only when a required rule
or safety invariant cannot be represented; do not rename or alias version-1
fields during the initial implementation. The schema must retain these
capabilities:

- enable/disable a stable built-in rule
- tune allowances and scoring within validated bounds
- enable and tune document-wide and rolling passage-density behavior per rule
  or category
- add, remove, or update curated words and literal/regex rules declaratively
- define repository terms and phrase exceptions
- bind an external custom rule to a named service and validated rule-specific
  settings
- set the threshold and category caps
- select Markdown contexts
- validate unknown keys, duplicate IDs, invalid regexes, negative costs,
  impossible caps, and unsupported schema versions as errors

Configuration can specialize built-in algorithms, define bounded phrase or
regex rules, and configure named services used by trusted custom Python rules.
It cannot import Python, execute commands, interpolate secret values, or create a
network rule without corresponding code in `CUSTOM_RULES`. More scan profiles
are outside the initial scope.

Calculate `config_digest` as SHA-256 over canonical JSON produced from the fully
validated effective configuration with sorted object keys. Secret values are
never part of configuration and therefore never enter the digest. Include every
enabled rule's ID/version and effective policy in the canonical value so reports,
external idempotency keys, and base/head reuse cannot cross policy revisions.

`slop-cop explain <rule-id>` should print effective configuration, rationale,
examples, exceptions, scoring group, and implementation kind. This is the
primary rule-debugging aid and makes tuning reviewable.

## Rule maintenance and custom-rule entry point

Easy rule maintenance is a required interface, not an implementation
convenience. The common operations must be:

| Operation | Required change |
| --- | --- |
| Add or update a word/phrase rule | Edit one declarative TOML block and its table-driven fixture cases |
| Disable a rule | Set `enabled = false`; retain the stable ID so existing suppressions receive a clear diagnostic |
| Remove a rule permanently | Remove its definition, tests, and obsolete suppressions in one change; registry validation identifies every dangling reference |
| Add a regex rule | Add one validated declarative TOML block with positive and counterexample cases |
| Add an algorithmic or service-backed rule | Add one module under `rules/custom/` and export one rule instance from `CUSTOM_RULES` |
| Promote a reusable custom rule | Move it into `rules/builtins/` without changing its ID or behavior contract |

Provide reusable implementations for literal phrases and bounded regular
expressions so those rules are data, not one-class-per-pattern Python code.
Provide helpers for normalized tokens, n-grams, sentence starts, paragraph
windows, exact source matches, bounded external requests, and validated audit
metadata so custom rules remain short.

Declarative regex patterns are limited to 500 characters and the explicit
`IGNORECASE`, `MULTILINE`, `DOTALL`, and `VERBOSE` flags. Reject inline flags,
backreferences, recursive/subroutine constructs, conditionals, and lookbehind.
Compile with `regex` and enforce the hard per-rule/file timeout during matching.
Python custom rules may implement more specialized parsing, but remain subject
to the same overall rule deadline and result bounds.

The custom Python template should require only:

```python
from slop_cop.rules.api import (
    FunctionRule,
    RuleContext,
    RuleEvaluation,
    RuleMetadata,
    RuleRuntime,
    RuleSignal,
)

METADATA = RuleMetadata(
    id="custom.repeated-claim-opener",
    version=1,
    category="repetition",
    title="Repeated claim opener",
    rationale="Repeated claim openings make consecutive paragraphs formulaic.",
    advice="Vary the paragraph structure or combine the claims.",
)


async def evaluate(
    context: RuleContext,
    runtime: RuleRuntime,
) -> RuleEvaluation:
    signals = tuple(
        RuleSignal(start=item.start, end=item.end, key=item.normalized)
        for item in context.repeated_sentence_starts(minimum_count=3)
    )
    return RuleEvaluation(signals=signals)


RULE = FunctionRule(metadata=METADATA, evaluator=evaluate)
```

Then `rules/custom/__init__.py` imports `RULE` and adds it to the explicit tuple:

```python
from .repeated_claim_opener import RULE as REPEATED_CLAIM_OPENER

CUSTOM_RULES = (REPEATED_CLAIM_OPENER,)
```

Add its policy separately:

```toml
[rules."custom.repeated-claim-opener"]
enabled = true
severity = "warning"
max_signal_units = 1
fixed_allowance = 0
first_cost = 3
repeat_cost = 2
cap = 9
on_error = "fail"
```

Use the immutable `FunctionRule` wrapper and module-level evaluator shown above.
Do not require custom rules to implement configuration parsing, Markdown
masking, line mapping, suppressions, scoring, serialization, or report rendering.

A service-backed evaluator uses the same entry point:

```python
JUDGE_METADATA = RuleMetadata(
    id="custom.editorial-judge",
    version=1,
    category="rhetoric",
    title="Editorial judge",
    rationale="The configured judge identified formulaic prose.",
    advice="Review the cited prose and replace generic phrasing with specifics.",
    execution_kind="external",
    services=("editorial_judge",),
)


async def evaluate(
    context: RuleContext,
    runtime: RuleRuntime,
) -> RuleEvaluation:
    response = await runtime.service("editorial_judge").post_json(
        {"schema_version": 1, "prose": context.projected_prose}
    )
    result = JudgeResponse.model_validate(response.data)
    signal = RuleSignal.document(
        key=result.label,
        units=result.strength,
        detail=result.explanation,
        evidence=context.map_exact_quotes(result.evidence),
    )
    audit = {**response.audit, "judge_revision": result.judge_revision}
    return RuleEvaluation(signals=(signal,), audit=audit)


JUDGE_RULE = FunctionRule(metadata=JUDGE_METADATA, evaluator=evaluate)
```

Export `JUDGE_RULE` from `CUSTOM_RULES`, add its `[rules]` policy block, and add
the named `[services.editorial_judge]` block. The custom module owns
`JudgeResponse` and its strict schema. Transport limits, secret handling, source
mapping, scoring, failure behavior, and reporting remain shared Slop Cop
behavior.

Add these focused development commands:

```text
slop-cop validate-rules
slop-cop list-rules --kind builtin|declarative|custom
slop-cop explain <rule-id>
slop-cop check --only-rule <rule-id> <fixture-or-note>
```

`validate-rules` must catch duplicate IDs, malformed metadata, invalid category
references, missing/nonpositive rule versions, scoring values outside configured
bounds, unsafe regexes, dangling
exceptions/suppressions, undeclared services, invalid failure policies, missing
judge revisions, invalid density units/windows/costs/caps, and rules without
positive and counterexample fixture coverage. `--only-rule` is diagnostic only
and cannot be used by the required CI decision.

Use one shared rule contract test suite against every built-in, declarative, and
custom rule. A contributor adding a custom rule supplies behavior cases through
`tests/rule_cases.toml` rather than building a separate test harness. Each entry
names a rule ID and defines positive inputs, counterexamples, expected spans, and
optional score-boundary cases. The contract suite must fail when an enabled
scored rule has no cases.

Use one simple case schema for every rule kind:

```toml
[[case]]
name = "not-just-visible-prose"
rule_id = "rhetoric.not-just"
kind = "positive"
source = "This is not just a wrapper."
expected_spans = [[8, 16]]

[[case]]
name = "not-just-inline-code"
rule_id = "rhetoric.not-just"
kind = "counterexample"
source = "Run `not just` as literal input."
expected_spans = []
```

Permit fixture-file references for complete Markdown and external-service cases,
but keep expected signals, spans, units, errors, and costs in the same case
record. The test harness, not each rule, owns parametrization and snapshot
formatting.

## Suppressions and manual override

### Finding-level suppressions

Support narrow source suppressions for known false positives:

```html
<!-- slop-cop: ignore-next=rhetoric.not-just reason="Contrasting two named API contracts" -->
```

The initial version supports only `ignore-next`; paired regions and file-wide
suppression are outside scope. Every suppression must name one or more stable
rule IDs and include a nonempty reason. Unknown rules, file-wide wildcards, and
missing reasons are configuration errors. Show all suppressions prominently in
terminal, JSON, and HTML output.

The directive must be a standalone HTML comment immediately before the next
scanned prose block. It suppresses the first finding for each named rule whose
start lies in that block; later findings remain active. A directive that does not
bind to a scanned block or suppress any named finding is an unused-suppression
error so stale exceptions cannot accumulate.

Do not permit source comments to set the global CI result or threshold.

### PR-level manual override

Use an approved PR review as the global manual override. A valid override is the
latest review that satisfies all of the following:

1. review state is `APPROVED`
2. the review is attached to the current PR head commit, not an earlier revision
3. the reviewer currently has `write`, `maintain`, or `admin` permission
4. the review body contains `Slop-Cop-Override: <nonempty reason>`

The analysis workflow should run on relevant `pull_request` events and on
`pull_request_review` submission/dismissal so a new valid review can replace a
failed result. A new commit invalidates the prior override automatically because
the approved review's commit no longer equals the head SHA.

A valid override changes the final CI conclusion to pass but does not alter
scores, hide findings, or label the document clean. The report and PR comment
must display `OVERRIDDEN`, the reviewer, reason, review URL/ID, and exact head
SHA. Invalid or stale override attempts should be reported as notices and have no
effect.

This is intentionally stricter than a persistent label: labels do not carry a
reason and can survive new commits accidentally. Do not add a second override
mechanism in the first release.

## HTML and machine reports

Generate one artifact directory per run:

```text
slop-cop-report/
├── index.html
└── report.json
```

`report.json` is the canonical machine result. Its version-1 top level must
contain at least:

```text
schema_version
analysis_state
decision
score                 # integer 0..100 or null
threshold
repository
pull_request_number   # null outside PR CI
base_sha
head_sha
tool_version
config_digest
files[]
rule_errors[]
external_audits[]
override              # null or validated override record
```

Each file record contains metrics, head/base results, findings, related and
suppressed findings, score arithmetic, density windows/costs, and errors. Define
all nested records as strict Pydantic models with bounded strings/lists and
`extra = "forbid"`. Serialize keys and arrays in stable documented order.

`index.html` must be self-contained, readable without a server, and usable with
JavaScript disabled. Use escaped HTML, inline CSS, semantic elements, and native
`<details>` controls. Do not fetch fonts, scripts, images, analytics, or other
network resources. Add a restrictive Content Security Policy such as
`default-src 'none'; style-src 'unsafe-inline'; img-src data:`.

The report should contain:

- prominent pass/fail/overridden state, PR score, threshold, and head SHA
- one summary row per changed note with head score, base score, and delta
- per-category and per-rule penalty arithmetic, including caps and allowances
- document-wide counts versus allowances plus each density-sensitive rule's
  configured window, densest passage, peak excess, bounded density bonus, and
  category-density contribution
- filterable-by-navigation sections for blocking, chargeable, advisory,
  suppressed, added, removed, and persistent findings
- path, line, column, escaped excerpt, nearby bounded context, rationale, advice,
  points, and related overlapping rules for each finding
- an escaped source view with highlighted findings and line anchors
- analyzed versus masked word counts and ignored-context explanations
- suppression and override audit details
- local/external execution kind, external service hostname, judge revision,
  latency, response digest, and incomplete/error state without secret or raw
  service payload disclosure
- tool version, configuration digest, JSON schema version, base/head revisions,
  and analysis errors
- a short “what this score does and does not mean” explanation

Keep source snippets bounded in `report.json`; the HTML may include the full
changed note because the artifact is repository-scoped, but it must never inject
unescaped source as markup or script. Do not include the full base document;
show only bounded before/after context for changed findings.

Make built-in analysis deterministic for a fixed input and configuration. Make
report rendering deterministic for a fixed `RunResult`. External judge output
may change between runs; isolate its audit metadata and returned signals so the
cause of a score change is visible. Put volatile timing and request metadata in
explicit fields that golden tests can normalize.

## GitHub Actions design

Reuse the repository's docs-preview trust pattern: an unprivileged PR workflow
performs analysis and uploads data; a separate trusted `workflow_run` workflow
validates the completed run and writes the PR comment. Never execute PR-supplied
code in the trusted commenting workflow.

### Analysis workflow: `slop-cop.yml`

Trigger on:

- `pull_request` opened, reopened, synchronize, and ready-for-review events
- `pull_request_review` submitted and dismissed for override refresh
- `push` to `main` for a full-corpus invariant check
- `workflow_dispatch` for maintenance

Use `contents: read`, `pull-requests: read`, `issues: read`, and no write
permissions. Concurrency should be keyed by PR number and cancel stale runs.
Inject service credentials only into the trusted-base analysis step and only
for named services enabled by the base configuration; do not expose them to
candidate project tests or candidate analyzer previews.

Normalize both event types into the same trusted inputs before checkout: PR
number, base SHA/repository, head SHA/repository, review event if present, and
changed paths. The required analysis job's displayed name must be exactly
`Slop Cop / Dev Notes` on every PR event so branch protection receives one
stable check context.

Run the workflow for every PR rather than relying on path filters for a required
check. Classify a run as:

- `ANALYZED` when a Dev Note was added, modified, or renamed
- `NOT_APPLICABLE` when no non-deleted Dev Note changed
- `ERROR` when inputs or analysis could not be completed

Always write and upload exactly one schema-valid artifact. A `NOT_APPLICABLE`
result has `score = null`, no synthetic 100 score, and an HTML page stating that
no Dev Note required analysis. The trusted commenter does not create a new PR
comment for this state and removes or marks obsolete an existing Slop Cop comment
if an earlier revision of the same PR was analyzed.

For PRs:

1. Resolve the PR, base SHA, head SHA, and changed Dev Note paths through the
   GitHub API or an explicit base/head diff. Handle additions, modifications,
   renames, and deletions; do not scan deleted files. Accept only regular UTF-8
   files lexically beneath the candidate repository root and reject symlinks.
2. Check out the candidate tree separately from the trusted analyzer tree.
3. Run the analyzer and policy from the PR's base revision against candidate
   Dev Note files. This prevents a PR from weakening Slop Cop's own code or
   configuration to pass itself. Separately test candidate changes under
   `dev-tools/slop-cop/` and run the candidate analyzer/configuration against the
   complete candidate Dev Note corpus. That non-authoritative preview prevents a
   checker change from surprising `main` after merge without letting it replace
   the trusted-base result for its own PR. Candidate tests must use fake service
   transports and receive no production service secrets.
4. Analyze base file content for comparison where it exists.
5. Query current-head approved reviews and validate a possible override.
6. Generate `index.html` and `report.json` under `$RUNNER_TEMP`, even when the
   policy result is fail.
7. Add bounded GitHub annotations for blocking and highest-cost findings, with
   a cap to avoid annotation spam. Put the complete result in the artifact.
8. Upload the report with `if-no-files-found: error` and a 14-day retention.
9. Write the same concise summary to the Actions job summary.
10. Only after upload, return pass, fail, or infrastructure-error according to
    the saved machine result and validated override.

GitHub does not provide ordinary Actions secrets to fork-originated
`pull_request` workflows. If a required external rule needs a secret, a fork PR
therefore produces a visible rule execution error and fails closed; a maintainer
may use the current-head manual override after reviewing the report. Do not use
`pull_request_target` or execute candidate code with secrets to bypass this
boundary. Do not enable a required external rule until this fork behavior is an
accepted repository policy.

Pin third-party actions to reviewed commit SHAs, set `persist-credentials:
false`, and use the committed `uv.lock`.

The introducing PR is a bootstrap exception because the workflow and trusted
base-revision analyzer do not yet exist on `main`; do not claim that its new
workflow has enforced the PR. Validate that PR with the full local suite and
ordinary repository review. After merge, require a successful full-corpus push
run on `main`, then exercise pass, fail, report, comment, stale-run, and override
behavior on disposable validation PR revisions. Enable the required branch
protection check only after those runs succeed.

On `main`, scan every Dev Note using the current checked-in tool and config.
Failing main protects against path-selection bugs and configuration changes that
would make accepted content fail unexpectedly.

### Trusted comment workflow: `slop-cop-report.yml`

Trigger on completion of the named analysis workflow. Give only `actions: read`,
`contents: read`, `pull-requests: write`, and any minimal comment permission the
GitHub API requires.

The workflow must:

1. Require a `pull_request`- or `pull_request_review`-originated workflow run,
   resolve its PR through trusted API metadata, and identify exactly one artifact
   whose name matches the strict PR/head pattern.
2. Verify the artifact PR is associated with the run and its recorded head SHA
   matches the workflow run and current PR head. Ignore stale runs.
3. Reject oversized artifacts and unknown JSON schema versions.
4. Download and parse only `report.json` with trusted checked-in code. Treat all
   strings as untrusted data; validate types, lengths, path prefixes, score
   ranges, counts, URLs, and override fields before interpolating Markdown.
5. Find the HTML artifact's GitHub URL through the Actions API.
6. create or update one bot comment containing `<!-- slop-cop-report -->`.

The sticky comment should show:

- status, PR score, threshold, and per-file scores
- base delta, category totals, blocking count, and top few findings
- override actor/reason when applicable
- a link to download the HTML report artifact
- the analyzed short SHA and artifact expiration note

Comment even when the analysis check fails, since failure is when the report is
most valuable. If artifact/comment publication fails, do not convert an analysis
failure to success or an analysis success to failure; the required analysis
check remains the source of truth. Report-publication failures should remain
visible as their own workflow failure.

## Evaluation and calibration

### Corpus

Create a small, versioned fixture corpus rather than a corpus-fitting subsystem:

- the current accepted Dev Note, split into representative prose and complete
  Markdown integration fixtures
- positive examples for each initial rhetorical construction
- positive examples for artifact, repetition, attribution, and rhythm rules
- synthetic “dense slop” documents combining several independent rule families
- legitimate technical counterexamples containing contrast, product vocabulary,
  numbered steps, bold lead-ins, lists, headings, and horizontal rules
- Markdown-context variants that place the same trigger in prose, code, a URL,
  front matter, generated byline, alt text, an HTML attribute, and a quote
- adversarial punctuation, casing, Unicode apostrophe/dash, and line-wrap variants
- fake external-judge responses for clean, chargeable, document-scoped,
  source-mapped, malformed, oversized, wrong-revision, timeout, and transport
  outcomes

Do not scrape or store unrelated prose. Add real false positives as minimized,
anonymized regression fixtures when reviewers encounter them.

### Rule-quality gates

Every scored rule must demonstrate:

- expected positive matches and exact spans
- nonmatches for its documented counterexamples
- punctuation, capitalization, line-wrap, and Unicode behavior
- Markdown context exclusions
- overlap behavior with related rules
- allowance and cost behavior at zero, first, repeat, and cap boundaries
- for a density-sensitive rule, below/at/above the passage allowance, rolling
  window boundaries, peak selection, and density-cap behavior

Use table-driven rule tests so additions remain reviewable. A rule with unresolved
common false positives stays advisory with zero points.

### Score-quality properties

Test these properties independently of exact golden scores:

- adding an unsuppressed chargeable finding cannot increase a score
- suppressing a finding cannot decrease a score
- duplicated overlapping detectors do not double charge a span
- one allowed/common construction does not fail an otherwise clean note
- diverse repeated signals reduce the score more than one isolated weak token
- for a density-sensitive rule, the same source-mapped signals cost more when
  concentrated in one configured passage than when spread across the note
- appending clean prose does not reduce an existing peak passage-density cost
- overlapping rolling windows never charge the same density peak more than once
- document-scoped signals and their display-only evidence do not enter
  passage-density math
- adding masked front matter, generated HTML, code, links, or quotes does not
  alter the score
- wrapping equivalent prose differently does not materially change the score
- no single weak vocabulary family can exhaust more than its category cap
- a clean second file cannot hide a failing first file
- a stale override never changes the decision
- identical validated `RuleEvaluation` values always produce the same score,
  regardless of async completion order
- an external rule error never becomes a zero-finding successful evaluation

### Initial calibration exit criteria

Before enabling the required threshold:

1. The current accepted Dev Note scores at least 80 without a file-wide
   suppression or manual override.
2. Each dense-slop fixture scores below 80 for more than one evidence family.
3. Every unambiguous pasted-assistant artifact fixture fails through a blocking
   rule or calibrated score.
4. Legitimate counterexamples pass and have no high-confidence false positive.
5. All context-invariance and score-property tests pass.
6. Density-sensitive rules have calibrated spread-versus-cluster fixtures and
   expose the complete peak-window arithmetic in golden results.
7. Two maintainers review the initial scored rule table, weights, density
   policies, threshold, and report wording as editorial policy, not only as code.

If the accepted Dev Note fails, diagnose individual false positives and scoring
assumptions. Do not simply lower the threshold or add a blanket suppression.

## Implementation sequence

### Phase 1: Scaffold and freeze contracts

1. Add `dev-tools/slop-cop/AGENTS.md`, `README.md`, `pyproject.toml`, locked
   environment, package skeleton, and test skeleton. The nested instructions
   must require direct implementation-focused writing and preserve the
   declarative and `CUSTOM_RULES` extension boundaries.
2. Create direct documentation boundaries: `README.md` owns installation and
   common commands; `docs/rules.md` owns rule APIs/configuration/cases;
   `docs/scoring.md` owns formulas and calibration; `docs/ci.md` owns workflows,
   artifacts, suppressions, and override operations. Do not duplicate normative
   details across those files.
3. Define immutable document, rule, finding, file-result, run-result, override,
   and versioned JSON models.
4. Define the `Rule`/`RuleContext`/`RuleRuntime`/`RuleEvaluation`/`RuleSignal`
   API, declarative rule and named-service schemas, `CUSTOM_RULES` entry point,
   stable rule-ID conventions, severity vocabulary, exit codes, and CLI
   snapshots.
5. Add the initial accepted, Markdown-context, counterexample, and dense-slop
   fixtures before implementing score tuning.

Exit gate: configuration and result schemas have round-trip tests; the CLI can
validate configuration and produce an empty typed run result.

### Phase 2: Build source-aware analysis

1. Implement the source-preserving Markdown projector and line index.
2. Add generated-byline awareness and strict suppression parsing.
3. Implement token, sentence, and paragraph segmentation with deterministic
   Unicode normalization that never loses original offsets.
4. Add exact source-span tests for every scanned and masked context.

Exit gate: all Markdown invariance tests pass against the complete current Dev
Note and minimized fixtures.

### Phase 3: Add rules and scoring

1. Implement pasted-artifact rules first, then rhetorical clichés and curated
   vocabulary, followed by repetition/rhythm and attribution rules.
2. Implement declarative phrase/regex construction, the explicit custom-rule
   registry, and the shared contract tests before adding specialized algorithms.
   Prove both extension paths with temporary representative rules in
   `test_rule_extension.py`; the test must add them without modifying or
   subclassing the engine, scorer, projector, CLI, or report renderer.
3. Implement the bounded named-service runtime, fake transport, async deadline,
   concurrency, response validation, audit metadata, and failure policies. Prove
   the external path with a fake LLM-judge service response; do not require a
   live service in unit tests.
4. Implement overlap grouping and mark structural rules advisory-only.
5. Implement natural-opportunity document allowances, rolling passage windows,
   peak-density selection, bounded rule/category density costs, and exact density
   audit records.
6. Implement the remaining per-rule, category-cap, file, and PR scoring model.
7. Implement `validate-rules`, `list-rules`, `explain`, `check --only-rule`,
   terminal output, JSON, and exit decisions.
8. Calibrate on the corpus and freeze golden results only after property tests
   pass.

Exit gate: the initial calibration criteria are satisfied and every score is
explainable as visible arithmetic.

### Phase 4: Add the HTML report

1. Render the self-contained accessible report from `RunResult`; do not rerun
   detectors in the renderer.
2. Add escaped highlighted source, base/head finding comparisons, audit details,
   and configuration identity.
3. Add golden structure, HTML-escaping, CSP, size-bound, and no-network tests.
4. Review the report manually using pass, fail, override, suppression, malformed
   input, and multiple-file fixtures.

Exit gate: opening `index.html` locally requires no server or network and cannot
interpret fixture text as markup or script.

### Phase 5: Integrate CI and override

1. Add the unprivileged analysis workflow with trusted-base execution, full
   report upload, annotations, job summary, and final decision.
2. Add current-head review-based override validation and tests using recorded
   GitHub API payload fixtures.
3. Add the trusted `workflow_run` commenter with artifact association, freshness,
   schema, size, and Markdown-injection validation.
4. Exercise internal and fork-style PRs for pass, fail, stale run, artifact
   failure, current override, stale override, renamed note, deleted note, and no
   relevant changes. Include external-rule success, timeout, invalid response,
   unavailable secret, advisory error, required error, and content-safe audit
   cases using a controlled test service.
5. Make `Slop Cop / Dev Notes` required only after the bootstrapping PR is on
   `main` and the calibration criteria remain satisfied there.

Exit gate: a failing PR still receives a downloadable report and sticky summary;
a valid override passes only the exact reviewed head revision.

### Phase 6: Post-merge stabilization without expanding scope

This phase is operational follow-up and does not block completion of the initial
implementation or its PR.

1. Observe the first five Dev Note PRs or the first 30 days, whichever comes
   first, and record false positives/negatives as minimized fixtures.
2. Adjust one rule or score assumption at a time with before/after corpus results.
3. Promote advisory structural rules only when evidence supports them.
4. Publish a short maintenance guide describing how to add a phrase, algorithmic
   rule, exception, fixture, or calibrated score change. Keep it procedural and
   limited to current Slop Cop interfaces.

Exit gate: no unresolved common false positives, all exceptions are narrow and
reasoned, and maintenance does not require knowledge of GitHub workflow internals.

## Security and integrity requirements

Use these initial hard bounds and expose lower configurable values where useful:

| Resource | Initial hard bound |
| --- | ---: |
| One Dev Note source | 1 MiB |
| Signals from one rule/file | 5,000 |
| Findings in one run | 20,000 |
| Regex evaluation for one rule/file | 250 ms |
| Concurrent external evaluations | 4 |
| One external response | 1 MiB; default service limit 64 KiB |
| Default external rule timeout | 20 seconds |
| Overall external-evaluation time per file | 60 seconds |
| GitHub annotations per run | 50 |
| Finding detail/explanation | 1,000 Unicode code points each |
| Generated HTML report | 10 MiB |

Exceeding a hard input, execution, response, or report limit is an analysis
error, not a truncated successful result. Finding/annotation presentation may be
truncated only after the complete bounded analysis result has been scored and
recorded in JSON.

- Built-in and declarative rules never send Dev Note content to a network
  service. Only an enabled trusted custom rule may send its explicitly selected
  projected prose through a configured named service.
- Do not execute Markdown, HTML, configuration values, regex replacements, or
  candidate-branch Python in the trusted reporting workflow.
- Expose service credentials only to trusted base-revision rule code; never put
  credentials or raw service payloads in logs, findings, JSON, HTML, comments,
  annotations, caches, or artifacts.
- Bound document size, individual match length, finding count, annotation count,
  regex input behavior, JSON size, excerpt size, and report size.
- Avoid catastrophic-backtracking patterns; prefer literal/token algorithms or
  statically reviewed bounded regexes. Add timeout/performance tests for the
  largest accepted input size.
- Escape source and findings independently for HTML and Markdown contexts.
- Use base-revision analyzer code and configuration for the required PR gate.
- Resolve scan paths beneath the explicit repository root and reject symlinks,
  devices, FIFOs, sockets, and paths escaping through `..` or absolute input.
- Bind overrides and artifact comments to the exact current head SHA.
- Do not expose full prose through action logs or annotations; keep bounded
  context in the access-controlled artifact.
- Keep dependency license records in the normal project metadata and lockfile;
  Slop Cop rule definitions and implementation text must be repository-owned.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| False positives make writers ignore the tool | Precision-first scored rules, allowances, advisory incubation, counterexamples, and narrow reasoned suppressions |
| Score implies an AI probability | Explicit contract and neutral wording in every output; never call it an authorship score |
| Document length distorts the result | Per-rule natural opportunities, document allowances, and rolling peak-passage density; no single global density formula |
| Many weak tokens overwhelm stronger evidence | Category caps, low vocabulary weights, overlap deduplication, and diverse-signal calibration |
| Markdown and generated sections pollute results | Same-length prose projection with integration fixtures from the real Dev Note |
| A PR modifies the checker to pass itself | Required gate executes analyzer and policy from the PR base revision |
| Override survives later changes | Current-head approved review with mandatory reason and permission verification |
| Fork PR cannot receive a comment | Unprivileged artifact producer plus trusted `workflow_run` commenter |
| HTML report enables injection | Escaped source, no external assets, no required JavaScript, CSP, and hostile golden fixtures |
| Artifact link is mistaken for hosted HTML | Comment says “download HTML report”; no Pages deployment in scope |
| Phrase list grows without quality control | Stable IDs, reviewable metadata, positive/counterexample tests, advisory-first policy, and measured calibration |
| One current Dev Note is too little calibration data | Pair it with targeted synthetic and legitimate fixtures; add minimized real regressions over time, not a fitting subsystem |
| External judge changes its answer between runs | Pin a service/judge revision where available, retain response digests and audit fields, cap its category cost, and keep the central scoring formula fixed |
| External service is unavailable or credentials are absent | Explicit per-rule failure policy; required scored rules fail closed and advisory rules mark the report incomplete |
| Dev Note text attempts to manipulate an LLM judge | Service-side no-tools structured judgment, strict response validation, bounded signal strength, fixed central scoring, and no document-controlled endpoint or prompt selection |

## Acceptance criteria

The initial implementation is complete when all of the following are true:

1. `uv run slop-cop check` produces deterministic built-in findings and scoring,
   exact source locations, and stable terminal, JSON, and HTML rendering for a
   fixed set of validated rule evaluations.
2. Front matter, generated bylines, code, destinations, markup, configured
   quotes, and suppression comments do not create findings or change the prose
   denominator.
3. The score arithmetic, allowances, overlap decisions, category caps, threshold,
   base delta, and final status are visible and reproducible from `report.json`.
4. The current accepted Dev Note passes the default threshold without a blanket
   exception.
5. Dense-slop and pasted-assistant fixtures fail, while legitimate technical
   counterexamples pass.
6. CI scans each changed Dev Note, gates on the minimum file score and blocking
   findings, and scans the complete corpus on `main`.
7. Pass, fail, and override runs all upload a self-contained HTML artifact and
   update one bounded sticky PR comment with a working artifact link.
8. A manual override requires a reasoned approved review from an authorized
   maintainer for the exact current head and remains conspicuous in all outputs.
9. Fork-style PRs cannot execute candidate code with write credentials or inject
   unvalidated artifact content into the trusted PR comment.
10. The project documentation explains limitations, rule maintenance,
    suppressions, score tuning, local use, CI behavior, and artifact expiration.
11. No generated report, score history, or downloaded artifact is committed to
    the repository.
12. The final change receives an editorial-policy review in addition to ordinary
    code review.
13. A phrase or bounded-regex rule can be added, updated, disabled, or removed
    through one declarative block plus table-driven cases, without editing the
    engine, scorer, projector, CLI, or report renderer.
14. An algorithmic or service-backed custom rule can be added through one module,
    one `CUSTOM_RULES` tuple entry, configuration, and table-driven cases,
    without editing any core Slop Cop module.
15. The shared rule contract suite runs against built-in, declarative, and custom
    rules and rejects duplicate IDs, invalid metadata, unsafe scoring values,
    dangling references, bad spans, and nondeterministic result order.
16. A focused review confirms Slop Cop documentation, source comments,
    docstrings, CLI text, reports, configuration examples, and test names
    describe only current behavior and repository requirements.
17. A fake external judge integration proves that a custom rule can make an
    asynchronous bounded request, validate a document-level judgment, map exact
    evidence when present, drive configured score units, and emit content-safe
    audit metadata.
18. Missing credentials, timeouts, transport errors, oversized responses,
    malformed judgments, and stale judge revisions follow the configured failure
    policy and can never silently produce a clean score.
19. Density-sensitive rule fixtures prove that concentrated findings receive a
    larger bounded penalty than the same findings spread across a note, clean
    appended prose cannot dilute the peak, and overlapping windows are not
    double charged.
20. Rule detection metadata and repository scoring policy remain separate;
    changing allowances, costs, caps, density, severity, or enabled state does
    not require changing Python detector code.
21. Terminal, JSON, HTML, annotations, job summary, and PR comment all derive
    from one serialized `RunResult` and agree on state, decision, score, and
    finding counts.
22. The initial production configuration contains no enabled custom Python rule,
    named external service, credential requirement, or placeholder integration;
    the complete custom local/external contract is proven with test-only rules.
